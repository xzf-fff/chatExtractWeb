DeepSeek 导出包结构详解Inside a DeepSeek export

把导出 ZIP 解压后只有四类文件，但它们的顺序、命名和互相引用关系都很讲究——chat-demo 的多数导入报错都能从这里找到解释。An unpacked export contains just four kinds of files, but their order, naming and cross-references are strict — which explains most chat-demo import errors.

目录结构Layout

deepseek_data-YYYY-MM-DD/
├── manifest.json              # 格式声明
├── user.json                  # 可选：账号信息
├── chat_session_index.json    # 会话索引（顶层数组）
└── chat_sessions/
    ├── <session-id>.json      # 单个会话正文
    └── <session-id>_files/    # 该会话的附件（图片等）

四类文件各管一件事：声明格式、列出有哪些会话、存放每个会话的正文、存放正文引用的附件。理解这个分工，就能理解为什么“只删掉几个会话文件”一定会导入失败。Four roles: declare the format, list the conversations, store each conversation, store the attachments they reference. Once you see the split, it is obvious why deleting a few session files always breaks the import.

manifest.json：为什么它必须是第一个条目manifest.json: why it must be the first entry

内容只有一行：{"export_format_version":3}。chat-demo 是**按条目流**解析 ZIP 的，读到第一个条目就判断“这是不是我认识的格式”，所以 manifest 一旦不在第一位，就会直接报「无法识别该文件」。It holds one line: {"export_format_version":3}. chat-demo parses the ZIP as a stream and decides from the first entry whether it recognises the format, so a manifest anywhere else produces “unrecognized file”.

用系统自带的“右键 → 压缩”重新打包，条目顺序通常会被打乱——这是最常见的自己坑自己。Re-zipping with the OS “Compress” command usually reorders entries — the most common self-inflicted failure.

chat_session_index.json：只是索引，不是正文chat_session_index.json: an index, not content

顶层是数组，每项形如：A top-level array whose entries look like:

{"id":"<uuid>","title":"会话标题","pinned":false,
 "message_count":52,
 "inserted_at":"2026-11-16T14:07:12.136Z",
 "updated_at":"2026-11-18T05:07:08.400Z"}
  • id 必须与 chat_sessions/<id>.json 的文件名一一对应，两个集合必须**完全相等**；id must map one-to-one to chat_sessions/<id>.json; the two sets must be exactly equal.
  • message_count 是冗余字段，只是给列表显示用；合并、裁剪后要按实际消息数重算。message_count is redundant — used for the list view, and must be recomputed after merging or pruning.
  • updated_at 决定默认排序，取错了会让列表顺序很怪。updated_at drives the default sort order.

会话是一棵消息树A conversation is a message tree

每个会话 JSON 里有 messages[] 和两个关键指针：每条消息的 parent_id，以及会话级的 current_message_id。前者把消息串成树（同一个 parent_id 下可以挂多条消息 → 分支），后者决定 demo 打开时显示哪条分支的末端。Each session has messages[] plus two pointers: each message's parent_id builds the tree (several messages may share a parent → branches), and the session-level current_message_id decides which branch end the demo opens.

"messages": [
  {"id":1,"parent_id":null,"role":"USER","status":"FINISHED",
   "fragments":[{"type":"REQUEST","content":"…"}]},
  {"id":2,"parent_id":1,"role":"ASSISTANT","status":"FINISHED",
   "fragments":[{"type":"RESPONSE","content":"…"}]}
],
"current_message_id": 2

片段（fragments）按类型区分：REQUEST/RESPONSE 是正文，THINK 是思考过程，TOOL_SEARCH/READ_LINK 是联网与阅读，FILE 是附件，CONTENT_RISK 是系统提示。想判断两条消息“内容是否相同”，比的就是这些片段。Fragments carry the payload: REQUEST/RESPONSE for text, THINK for reasoning, TOOL_SEARCH/READ_LINK for web activity, FILE for attachments, CONTENT_RISK for system notices. Comparing fragments is how you decide whether two messages are “the same”.

改消息一定要同步这两处：删掉一条消息却留着指向它的 parent_id，就会报「消息分支已损坏」。Always fix both pointers: delete a message while something still points at it and you get “message branch is broken”.

附件与 export_pathAttachments and export_path

FILE 片段的 files[] 里有 export_path，形如 chat_sessions/<会话 id>_files/<fileId>_<文件名>。这个字符串就是包内真实路径，必须逐字一致；文件名含中文等非 ASCII 字符时，demo 会直接拒收整个包。A FILE fragment's files[] carries export_path such as chat_sessions/<session-id>_files/<fileId>_<name>. That string is the real path inside the archive and must match verbatim; non-ASCII names make the demo reject the whole package.

三个常见误解Three myths

  1. 「消息 id 是稳定标识」——不是。每次导出会重新编排 id，删过消息后后面的 id 整体前移；跨导出按 id 对比会整段错位。“Message ids are stable” — no. Every export renumbers ids; deleting messages shifts later ones, so comparing two exports by id misaligns whole stretches.
  2. 「改正文就够了」——改完还要保证 parent_id、current_message_id 仍然指向存在的消息，时间戳仍是 YYYY-MM-DDTHH:MM:SS.mmmZ。“Editing text is enough” — you must also keep parent_id/current_message_id pointing at existing messages and timestamps in YYYY-MM-DDTHH:MM:SS.mmmZ.
  3. 「索引可以手工留着」——裁剪会话文件时必须同步裁剪索引，否则报「文件内容不完整」。“The index can stay as is” — pruning sessions requires pruning the index too, otherwise “incomplete content”.

想自己改包，至少守住四条Four rules if you edit by hand

  1. manifest.json 永远是第一个条目；manifest.json stays first.
  2. 索引的 id 集合 = 包内会话文件 id 集合；Index ids = packaged session ids.
  3. 附件路径原样复制，不改名；Copy attachment paths verbatim.
  4. 时间戳格式、role/status 枚举、父链自洽。Timestamps, role/status enums, consistent parent links.

四条都满足，包就能导入；任何一条不满足，chat-demo 只会给一句笼统的报错。用 子集提取器 或 版本合并器 打包时，这四条会在导出前自动校验、导出后自动复解析，不用你记。Meet all four and it imports; miss one and chat-demo only gives a generic error. The subset extractor and version merger validate all four before export and re-parse the result afterwards, so you don't have to remember them.
