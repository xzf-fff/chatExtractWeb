Merging two exports

The same conversation exported on two dates, each with its own additions and edits. Merging is a union by aligned message, not one export overwriting the other.

When you need it

  • Exported once before and once after switching devices or accounts.
  • You export periodically and want one complete archive.
  • An old package overwrote a new one (losing new messages) or vice versa (losing a branch).

Importing either package loses something: the old one lacks later messages, the new one may lack old branches. Merging takes the union of both.

Two ground rules

  1. Group by conversation id: only the same id counts as two versions of one conversation, so both exports must come from the same account.
  2. Align by message id (after realignment when needed, below): a message may be identical, edited, or present in only one version.

What counts as a conflict

Compare role, parent_id and fragments (text / thinking / tool results). Metadata-only differences are not conflicts:

  • timestamps (including published_at in search results), token counts, width/height, file size, file_id;
  • one extra or missing CONTENT_RISK/TIP system notice;
  • empty fragments (e.g. an extra empty REQUEST).

The effect is large: for one 406-message conversation a raw comparison reported 210 conflicts; after ignoring the noise above, 24; after fixing the id offset below, 0 — the text had not actually changed at all.

Message ids get renumbered

Each export renumbers message ids: deleting messages shifts every later id. In one real pair the same message was #383 in the older export and #373 in the newer one — a 10-id offset from that point on, which pairs every message with its neighbour and floods you with false conflicts.

The fix is to align the role + text sequences first (LCS), normalise both exports to one numbering, and only then compare by id. The tool does this automatically when it detects a clear offset and tells you once; when ids already agree nothing is renumbered.

Choosing the branch head

A conversation is a tree and current_message_id decides which branch end the demo opens. Merging defaults to the newest version's head, falling back to an existing leaf. Unselected branches are kept in full and can be switched from the dropdown later.

Export and verify

  • the index recomputes message_count and sets pinned to false;
  • attachments are the union of all versions, preferring the newer one on the same path;
  • validated against chat-demo's rules before export, then re-parsed afterwards (first entry, order, CRC, index consistency);
  • importing replaces the demo's local conversations — back up first.

Four pitfalls

  1. Wrong package: one export holds hundreds of conversations, the other one — the list then shows hundreds of rows, almost all marked “only B”.
  2. Exporting everything: many rows stay selected by default; switch to “with differences” and tick just the conversation you mean.
  3. Thinking one-sided messages are dropped: they are kept automatically, no action needed.
  4. Message count grows: the union includes messages on unselected branches, so the total can exceed either version — expected.
