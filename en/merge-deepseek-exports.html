两次导出怎么合并Merging two exports

同一组对话在两个日期各导出一次，两份各有新增和改动。合并不是「谁覆盖谁」，而是按消息对齐后取并集。The same conversation exported on two dates, each with its own additions and edits. Merging is a union by aligned message, not one export overwriting the other.

什么时候需要合并When you need it

  • 换设备、换账号前后各导出过一次；Exported once before and once after switching devices or accounts.
  • 习惯定期导出，想把几次导出并成一份完整存档；You export periodically and want one complete archive.
  • 用旧包覆盖了新包（丢掉新消息），或者反过来（丢掉旧分支）。An old package overwrote a new one (losing new messages) or vice versa (losing a branch).

直接选一个包导入都会丢东西：旧包缺后来的对话，新包可能缺当年删过、后来分支出来的内容。合并的目标是把两边的消息**取并集**。Importing either package loses something: the old one lacks later messages, the new one may lack old branches. Merging takes the union of both.

两条基本规则Two ground rules

  1. 按会话 id 分组：只有会话 id 相同，才会被当作「同一对话的不同版本」。所以两份导出必须来自同一个账号。Group by conversation id: only the same id counts as two versions of one conversation, so both exports must come from the same account.
  2. 按消息 id 对齐（必要时先按正文重排，见下节）：同一条消息在两版里可能是「完全相同」「被改过」「只在一版存在」三种情况。Align by message id (after realignment when needed, below): a message may be identical, edited, or present in only one version.

什么算冲突What counts as a conflict

比较 role、parent_id 与 fragments（正文/思考/工具结果）。但**只差元数据不算冲突**：Compare role, parent_id and fragments (text / thinking / tool results). Metadata-only differences are not conflicts:

  • 时间戳（含联网搜索结果的 published_at）、token 统计、宽高/文件大小、file_id；timestamps (including published_at in search results), token counts, width/height, file size, file_id;
  • CONTENT_RISK/TIP 这类系统提示多一条少一条；one extra or missing CONTENT_RISK/TIP system notice;
  • content 为空的空片段（例如一边多一个空 REQUEST）。empty fragments (e.g. an extra empty REQUEST).

实际效果很明显：某会话 406 条消息，按原始字段比对会得到 210 条「冲突」；滤掉上述噪音后是 24 条；再修正下面的 id 错位后是 0 条——那份数据两版正文其实一条都没改。The effect is large: for one 406-message conversation a raw comparison reported 210 conflicts; after ignoring the noise above, 24; after fixing the id offset below, 0 — the text had not actually changed at all.

消息 id 会被重排Message ids get renumbered

每次导出会重新编排会话内的消息 id：中间删过消息后，后面的 id 整体前移。实测两份导出里，同一条「2022地市」在旧包里是 #383、在新包里是 #373，从那里开始整段错位 10。此时按 id 对齐，会把每一条都配给「隔壁」的消息，满屏假冲突。Each export renumbers message ids: deleting messages shifts every later id. In one real pair the same message was #383 in the older export and #373 in the newer one — a 10-id offset from that point on, which pairs every message with its neighbour and floods you with false conflicts.

解决办法是先用「角色 + 正文」做序列对齐（LCS），把两份导出的 id 归一化到同一套编号，再按 id 比较。工具会在检测到明显错位时自动这么做，并弹一次提示；id 本来就一致时不会重排。The fix is to align the role + text sequences first (LCS), normalise both exports to one numbering, and only then compare by id. The tool does this automatically when it detects a clear offset and tells you once; when ids already agree nothing is renumbered.

当前分支怎么选Choosing the branch head

会话是消息树，current_message_id 决定 demo 打开时显示哪条分支的末端。合并默认取最新版本的 head；如果那条消息在合并结果里不存在，就退回一个真实存在的叶子。未选中的分支不会丢，仍然完整保留在消息里，随时可以在右栏下拉切换。A conversation is a tree and current_message_id decides which branch end the demo opens. Merging defaults to the newest version's head, falling back to an existing leaf. Unselected branches are kept in full and can be switched from the dropdown later.

导出与验证Export and verify

  • 索引按合并结果重算 message_count，pinned 统一为 false；the index recomputes message_count and sets pinned to false;
  • 附件取各版本的并集，同路径优先较新版本；attachments are the union of all versions, preferring the newer one on the same path;
  • 导出前按 chat-demo 规则校验，导出后复解析自检（首条目、顺序、CRC、索引一致性）；validated against chat-demo's rules before export, then re-parsed afterwards (first entry, order, CRC, index consistency);
  • 导入 demo 会覆盖本地对话，先备份。importing replaces the demo's local conversations — back up first.

四个常见坑Four pitfalls

  1. 拿错包：一份是全量导出（几百组），另一份只含一个会话，列表当然显示几百组、而且几乎全是「仅 B」。Wrong package: one export holds hundreds of conversations, the other one — the list then shows hundreds of rows, almost all marked “only B”.
  2. 全选导出：默认会保持较多的勾选，只想合并某一组就切到「有差异」再单独勾。Exporting everything: many rows stay selected by default; switch to “with differences” and tick just the conversation you mean.
  3. 以为「仅一侧」被丢了：只在一边存在的消息会自动保留，不需要你选。Thinking one-sided messages are dropped: they are kept automatically, no action needed.
  4. 合并后条数变多：并集会包含未选中分支上的消息，所以数量可能大于任一单版本，这是正常的。Message count grows: the union includes messages on unselected branches, so the total can exceed either version — expected.
