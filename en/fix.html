「无法识别该文件」“Unrecognized file”

现象：选完 ZIP 立刻报错，连导入进度都没有出现。Symptom: the error appears right after picking the ZIP, before any progress.

原因：包内第一个条目不是 manifest.json，或缺少 export_format_version: 3。demo 按条目流顺序解析，先读 manifest 判断格式；用系统压缩工具（右键 → 压缩）重打一次包，就会把条目顺序打乱。Cause: manifest.json is not the first entry, or export_format_version: 3 is missing. The demo parses the archive as a stream and reads the manifest first; re-zipping with the OS “Compress” command reorders entries.

解决：用本工具导出（固定把 manifest 写成第一个条目），不要用系统压缩工具二次打包。Fix: export with these tools (manifest is always written first); never re-zip with the OS archiver.

「文件内容不完整」“Incomplete content”

现象：导入进行到一半中止，会话列表没有更新。Symptom: the import stops midway and the conversation list stays unchanged.

原因：chat_session_index.json 里的会话 id 集合与包内 chat_sessions/*.json 不完全相等（多一个少一个都不行）；或者索引被排在了会话文件之前——demo 会把后面的会话当成附件。Cause: the ids in chat_session_index.json do not exactly match the packaged chat_sessions/*.json; or the index sits before the session files, so later entries get treated as attachments.

解决：只保留部分对话时，必须同时裁剪索引；顺序固定为 manifest → user.json → 会话 → 索引 → 附件。Fix: when keeping a subset, prune the index too; the order must be manifest → user.json → sessions → index → attachments.

「消息分支已损坏」“Message branch is broken”

现象：导入成功，但打开某个对话时报错或显示空白。Symptom: import succeeds, but opening a conversation fails or shows nothing.

原因：current_message_id 或某条消息的 parent_id 指向了不存在的消息。手工拼接两份导出、或合并后没有重算消息 id 与父链时最容易触发。Cause: current_message_id or some message's parent_id points at a message that does not exist — typical when splicing two exports together or merging without recomputing ids and parents.

解决：用版本合并器重新合并：它会按内容对齐两份导出、重算消息 id 与父链，并让「当前分支」指向真实存在的叶子。Fix: re-merge with the version merger: it aligns both exports by content, recomputes message ids and parent links, and points the current branch at an existing leaf.

「附件数据已损坏」“Attachment data is corrupt”

现象：正文能看，但图片全部裂开。Symptom: text renders but every image is broken.

原因：FILE 片段里的 export_path 与包内实际路径不一致，或附件文件缺失；另外条目名含非 ASCII 字符（例如中文文件名）也会被 demo 拒绝。Cause: the FILE fragment's export_path does not match the packaged path, or the file is missing; non-ASCII entry names (e.g. Chinese filenames) are also rejected.

解决：附件保持 chat_sessions/<会话 id>_files/<文件名> 原路径原样复制，不改名、不移动。Fix: copy attachments verbatim to chat_sessions/<session-id>_files/<filename> — no renaming, no moving.

为什么手改 ZIP 容易坏Why hand-editing a ZIP breaks

demo 的导入器比大多数工具严格，四条硬约束叠在一起，手工操作很容易踩中其中一条：The demo's importer is stricter than most tools; four hard constraints stack up:

  1. 条目顺序：manifest 必须第一个，附件必须在索引之后。Entry order: manifest first, attachments after the index.
  2. id 集合相等：索引与包内会话文件必须一一对应。Matching id sets: index entries and session files must correspond one to one.
  3. ZIP 限制：只接受 Store / Deflate，不支持 ZIP64、data descriptor、加密包和非 ASCII 条目名。ZIP limits: Store/Deflate only; no ZIP64, data descriptor, encryption, or non-ASCII entry names.
  4. 字段校验：时间戳格式、role/status 枚举、parent_id 与 current_message_id 必须自洽。Field checks: timestamp format, role/status enums, and self-consistent parent_id/current_message_id.

用工具一次解决Fix it in one go

两个工具在导出前都会按上面四条逐项校验，发现错误直接阻止导出并指出具体会话；导出后还会重新解析成品做自检（首条目、顺序、CRC、索引一致性），通过才给你下载。所以只要用它们打包，这四种报错基本不会出现。Both tools validate all four rules before exporting, block on errors with the offending conversation named, then re-parse the produced ZIP (first entry, order, CRC, index consistency) before offering the download — so these four errors practically disappear.
