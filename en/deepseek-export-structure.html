Inside a DeepSeek export

An unpacked export contains just four kinds of files, but their order, naming and cross-references are strict — which explains most chat-demo import errors.

Layout

deepseek_data-YYYY-MM-DD/
├── manifest.json              # 格式声明
├── user.json                  # 可选：账号信息
├── chat_session_index.json    # 会话索引（顶层数组）
└── chat_sessions/
    ├── <session-id>.json      # 单个会话正文
    └── <session-id>_files/    # 该会话的附件（图片等）

Four roles: declare the format, list the conversations, store each conversation, store the attachments they reference. Once you see the split, it is obvious why deleting a few session files always breaks the import.

manifest.json: why it must be the first entry

It holds one line: {"export_format_version":3}. chat-demo parses the ZIP as a stream and decides from the first entry whether it recognises the format, so a manifest anywhere else produces “unrecognized file”.

Re-zipping with the OS “Compress” command usually reorders entries — the most common self-inflicted failure.

chat_session_index.json: an index, not content

A top-level array whose entries look like:

{"id":"<uuid>","title":"会话标题","pinned":false,
 "message_count":52,
 "inserted_at":"2026-11-16T14:07:12.136Z",
 "updated_at":"2026-11-18T05:07:08.400Z"}
  • id must map one-to-one to chat_sessions/<id>.json; the two sets must be exactly equal.
  • message_count is redundant — used for the list view, and must be recomputed after merging or pruning.
  • updated_at drives the default sort order.

A conversation is a message tree

Each session has messages[] plus two pointers: each message's parent_id builds the tree (several messages may share a parent → branches), and the session-level current_message_id decides which branch end the demo opens.

"messages": [
  {"id":1,"parent_id":null,"role":"USER","status":"FINISHED",
   "fragments":[{"type":"REQUEST","content":"…"}]},
  {"id":2,"parent_id":1,"role":"ASSISTANT","status":"FINISHED",
   "fragments":[{"type":"RESPONSE","content":"…"}]}
],
"current_message_id": 2

Fragments carry the payload: REQUEST/RESPONSE for text, THINK for reasoning, TOOL_SEARCH/READ_LINK for web activity, FILE for attachments, CONTENT_RISK for system notices. Comparing fragments is how you decide whether two messages are “the same”.

Always fix both pointers: delete a message while something still points at it and you get “message branch is broken”.

Attachments and export_path

A FILE fragment's files[] carries export_path such as chat_sessions/<session-id>_files/<fileId>_<name>. That string is the real path inside the archive and must match verbatim; non-ASCII names make the demo reject the whole package.

Three myths

  1. “Message ids are stable” — no. Every export renumbers ids; deleting messages shifts later ones, so comparing two exports by id misaligns whole stretches.
  2. “Editing text is enough” — you must also keep parent_id/current_message_id pointing at existing messages and timestamps in YYYY-MM-DDTHH:MM:SS.mmmZ.
  3. “The index can stay as is” — pruning sessions requires pruning the index too, otherwise “incomplete content”.

Four rules if you edit by hand

  1. manifest.json stays first.
  2. Index ids = packaged session ids.
  3. Copy attachment paths verbatim.
  4. Timestamps, role/status enums, consistent parent links.

Meet all four and it imports; miss one and chat-demo only gives a generic error. The subset extractor and version merger validate all four before export and re-parse the result afterwards, so you don't have to remember them.
