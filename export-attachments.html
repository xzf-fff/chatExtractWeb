导出里的图片和附件怎么处理Images and attachments in an export

对话正文是 JSON，图片是独立文件。两者靠一个字符串（export_path）相连——这正是导入后「图片全裂」最常见的原因。Text lives in JSON, images live as separate files, and a single string (export_path) connects them — which is exactly why images often break after import.

附件存在哪里Where files live

每个会话一个目录，命名规则固定：Each conversation gets one folder, named by convention:

chat_sessions/
├── <session-id>.json          # 会话正文
└── <session-id>_files/        # 这个会话的所有附件
    ├── <fileId>_image.png
    └── <fileId>_image.png

文件名前缀是文件 id（UUID），后缀是原始文件名。图片通常叫 image.png，所以同一个会话里会出现很多同名文件——靠 fileId 前缀区分。The prefix is the file id (a UUID) and the suffix is the original name. Images are usually called image.png, so a conversation can contain many same-named files distinguished only by the id prefix.

export_path 是什么What export_path is

消息里的附件不是二进制，而是一个 FILE 片段，里面列出文件元信息：Attachments inside a message are not binary data but a FILE fragment listing metadata:

{"type":"FILE","files":[
  {"id":"d4108600-…","file_name":"image.png",
   "export_path":"chat_sessions/<session-id>_files/d4108600-…_image.png",
   "file_size":142341,"is_image":true,"width":1400,"height":985}
]}

export_path 是包内相对路径，必须与真实文件位置**逐字一致**。它是唯一把「消息」和「文件」连起来的线索——写错一个字符，图片就读不到。export_path is the relative path inside the archive and must match the real file location verbatim. It is the only link between a message and its file; one wrong character and the image cannot be loaded.

图片为什么会裂Why images break

  • 只拷了 JSON：把 chat_sessions/*.json 打包却漏了 _files/，正文能看、图片全空。Only the JSON was copied: packing chat_sessions/*.json without _files/ keeps text but leaves every image blank.
  • 路径被改写：把文件挪进别的目录、或重新命名后没同步 export_path。Paths were rewritten: moving or renaming files without updating export_path.
  • 文件大小写不一致：Windows 不区分大小写，导入端区分。Case mismatch: Windows ignores case, the importer does not.
  • 非 ASCII 文件名：中文文件名会让 chat-demo 拒绝整个包（它的 ZIP 解析器不接受非 ASCII 条目名）。Non-ASCII names: Chinese filenames make chat-demo reject the whole package — its ZIP parser refuses non-ASCII entry names.
  • 合并时漏取并集：两份导出的附件分属不同目录，只打包其中一份就会缺图。Merge took only one side: attachments live in per-export folders, so packing one side loses the other's images.

打包时的四条规则Four packaging rules

  1. 附件必须和会话一起打包，路径保持 chat_sessions/<id>_files/<文件名>；Pack attachments with their conversation, keeping chat_sessions/<id>_files/<name>;
  2. 不改名、不移动、不重新压缩图片；never rename, move or recompress them;
  3. 条目名只能是 ASCII 字符；entry names must be ASCII only;
  4. 合并多份导出时，附件按路径取并集（同路径优先较新版本）。when merging exports, union attachments by path (prefer the newer version on the same path).

子集提取器 在导出前会检查每个 export_path 是否以该会话的 _files/ 开头、文件是否真的存在、名字是否 ASCII；版本合并器 会把各版本的附件目录取并集。任何一项不满足都会阻止导出并指出是哪个会话。The subset extractor checks that every export_path starts with that conversation's _files/, that the file exists and that the name is ASCII; the version merger unions attachment folders across versions. Any failure blocks the export and names the conversation.

体积与实际数量Size in practice

图片是导出包里最占体积的部分：一份几百组对话的导出里，带图的会话可能只有个位数，但图片本身常有几十 MB（截图按原尺寸保存）。勾选时工具会实时显示「原始体积」，几十组带截图会对体积影响很大。Images dominate package size: a several-hundred-conversation export may have only a handful of image-bearing chats, yet the images alone can run to tens of MB at full resolution. The tool shows the running size while you select.

分享前注意Before sharing

导出里的图片绝大多数是聊天截图，可能包含手机号、地址、账户界面等个人信息。生成的 ZIP 会把这些图片原样带出——分享到群聊或公共网盘前请逐张确认，或先用工具只挑需要的会话。Most exported images are screenshots that may contain phone numbers, addresses or account screens. The ZIP carries them verbatim, so review them before sharing to group chats or public drives — or select only the conversations you need.
